## Known constraints, fixed before development started

- **Launch is button-triggered from the local console, not scheduled.** There's no wake alarm for the PC, no auto-start, and no auto-shutdown when done. The user opens the console themselves (`uv run python scripts/console.py`) and presses "Assemble newspaper" whenever they want; the same run is also available from the terminal (`uv run tg-newspaper`) for a headless run without a browser. The collection window is always a fixed last 24 hours **from the moment the button is pressed**, not "since the last successful run" — catching up on missed runs is deliberately not implemented; every run simply takes its own last 24 hours.
- **One-click console launch.** `scripts/make_app.sh` builds `TG Newspaper.app` (by default under `~/Applications`, not committed to the repo); the app invokes `scripts/launch.sh`: it finds uv, runs `uv sync` and `playwright install chromium`, starts the console in the background (log at `data/console.log`, pid at `data/console.pid`) and opens the browser; if the console is already responding on its port, it just opens a tab. It's stopped via the "Shut down console" button on the home page (`POST /shutdown`). For testing: `TG_NEWSPAPER_PORT`, `TG_NEWSPAPER_RUN_DIR`, `TG_NEWSPAPER_NO_OPEN`.
- **Releases (macOS dmg, Windows setup.exe).** User data is separated from the app via the `TG_NEWSPAPER_HOME` variable (`config.home_dir()`; without it, the repo root is used, so dev mode is unaffected): `.env`, `config/channels.yaml`, `data/` (DB, photos, logs, pid), and the Telethon session all live under it; the individual `TG_NEWSPAPER_ENV/CHANNELS/SESSION_DIR/DB` variables take priority over it. In a release, the app (`scripts/build_release_mac.sh`, `packaging/windows/`) ships only source code; when `TG_NEWSPAPER_HOME` is set, `scripts/launch.sh` (and `packaging/windows/launch.ps1`) installs uv if needed, runs `uv sync --frozen --no-editable --reinstall-package tg-newspaper` into `$TG_NEWSPAPER_HOME/venv`, shows a waiting page (`scripts/preparing.html`), and launches the console with the venv's interpreter. Data paths only ever go through `config.py`'s functions (`env_path/channels_path/db_path/media_dir`), never from `__file__`. The launchers set `PYTHONUTF8=1` (otherwise, on Windows, stdout piped to a file ends up as cp1251). Build and release — `.github/workflows/release.yml` on tag `v*`; icons are pre-built assets in `packaging/icons/` (`scripts/make_icons.py`, run once). No code signing; Playwright is pinned to 1.50.0 — don't bump it.
- **Channel access is MTProto under a user account (Telethon), not the Bot API.** Bots have no method to "hand over a channel's history for a period" — they only receive posts as they appear (`getUpdates`/webhook) while connected. That's incompatible with the agent's design: collection must be able to return a channel's history for an arbitrary "back from this point" period on demand, not just listen for new messages. MTProto can return history on request — that's the decisive reason for the choice, not just a preference. Details: "Why MTProto instead of the Bot API" in [README.md](README.md) and the "Collecting posts" section in [docs/project-brief.md](docs/project-brief.md).
- **The Telethon session is the key to the Telegram account, not a token with limited rights.** Store it as a secret, never commit it to the repo, never log it. The account is a separate one, set up specifically for this project, not the main personal account: a leaked session only compromises that one.
- **The printer (HP Color LaserJet Pro MFP M377dw) only prints over the local network.** Cloud printing is physically unavailable for this model: HP shut down the ePrint service in January 2023 (it had already stopped shipping it on new printers back in 2020), and Google Cloud Print was shut down by Google even earlier, at the end of 2020. The printing code must run on the same local network as the printer (AirPrint/CUPS/IPP) — a cloud-render-plus-email-print architecture does not work for this printer and never will.

## The project

A pilot project: the idea is to replace morning feed-scrolling with a printed newspaper issue of fixed length, which an agent assembles and prints by itself, with no human involved. The issue is a poster-style front page (one merged sheet = 2 landscape pages, styled after the Daily Bugle's cover look: loud LLM-written announcements, photos, a black masthead plate reading `DAILY · TIMOHA`; it never prints articles at all) plus up to 6 landscape mosaic pages (`pipeline.NEWSPAPER_MAX_PAGES`; one A3 sheet = 2 pages), where all the news actually runs in full. Rendering is HTML/CSS + Playwright/Chromium (`src/tg_newspaper/layout.py`); whatever doesn't fit is decided by the LLM importance score (`classifier.py`) — either shortened by the model or dropped — rather than printed haphazardly. Work through the stages in implementation-plan.md, without getting ahead of the open questions in future-development.md.

## History for dedup — actually assembled issues

Dedup against what's already been published (`history_dedup.filter_against_history`) compares candidates against posts from the last 5 **assembled issues** (the `issue_posts` table, the printed text after shortening), not against `pipeline_outcomes.included=1` and not against the last 5 runs: `included` only means "passed selection" — some such posts don't end up fitting in the issue. The issue's contents are written by `pipeline.save_newspaper_issue(conn, run_id, result)`, called from `pipeline.assemble_issue(config, conn, run)` — the single issue-assembly path shared by the console button, `uv run tg-newspaper`, and `scripts/render_preview.py` (printing should eventually go through it too). Issue files live in `data/issues/run_<id>/` (next to the DB): pages `page_N.png` and a lazily built cache of `a4.pdf`/`a3.pdf` (`issue_pdf.build_pdf`); `assemble_issue` deletes old pages and PDFs before rebuilding; re-assembling the same `run_id` replaces its contents. In a DB created before this change, the history is empty until the first issue is assembled.

**Issue threshold.** If the number of news items with `included=1` is below `pipeline.MIN_ISSUE_NEWS` (= `layout.COVER_MIN_ARTICLES` = 10: lead + `COVER_SECONDARY_COUNT` + `TEASER_TOP_COUNT` + `COVER_TERTIARY_COUNT`, i.e. that many cover slots; with fewer, the last row stays incomplete), `assemble_issue` returns None before touching any files or the DB; the check is done by `enough_news_for_issue`, and the user-facing text by `few_news_message` (CLI, `render_preview.py`, the run page; the "Lay out issue" button isn't shown, and already-laid-out pages stay as they are). **Time:** the DB always stores UTC; everything shown to the user (run dates in the console, the issue date, the PDF name) is converted to the system's local timezone via `layout.to_local`. The cover edition (Morning/Afternoon/Evening/Night edition) is picked from the local hour at the end of the run window, via `layout.edition_name`. "Issue No. 0" on the cover is intentional (the pipeline doesn't pass `issue_number`) and isn't meant to be fixed until development is finished: see "Before finishing development" in [docs/implementation-plan.md](docs/implementation-plan.md).

## Sections and the "New videos" block in layout (Stage 7)

Without sections in `channels.yaml`, the issue lays out exactly as before. With sections, `layout._build_bands` distributes news into sections (in `rubric_order`; channels with no section go last, under a "Misc" section; channel matching is case-insensitive); tiers (one lead story per issue, `FEATURE_SLOTS` feature items, the rest brief) are decided globally by importance, while grouping into rows happens within each section. A section heading is a special `_Band` (`kind="header"`), placed on a page only together with the first row of its section, and repeated with "(continued)" if the section spills onto a new page. Section order is strict: a deferred (unfit) row from one section blocks the following sections on that page (`_fill_sheet`), which is why there can be empty space at the bottom of a page — a deliberate trade-off for keeping sections contiguous. This can also happen without any sections: a row that doesn't fit in the remaining space on a page moves to the next page, leaving roughly 1/5 of a page empty at the bottom (a known limitation, see "Deferred features" in [docs/future-development.md](docs/future-development.md)). The cover picks announcements by importance among whatever fit (`_importance_order`), not by row order. The "New videos" block (`kind="videos"`, up to `MAX_VIDEOS`, color thumbnails from `thumbnail_path`) is the last section in the queue; on the last allowed `max_pages` page, space for it is reserved in advance, so news items can't push it out — they go to leftover instead. So when there's nothing left to shorten, `build_newspaper` doesn't just drop the leftover outright — it does a binary search for the largest number k of the issue's most important news items that fits completely (every probe is `render_pages(fit_only=True)`: no cover, no LLM, no disk writes; there's exactly one full render with announcements into the issue directory, at the end, so no stray `page_N.png` files are left over from a longer attempt; if the final result still produces leftover, those posts don't make it into the issue's contents — they go to dropped), then drops the rest (otherwise, with sections, the tail of the last section would get dropped even if important; and dropping `len(leftover)` all at once freed up far more space than needed, leaving the last pages empty).

**Mosaic capacity (decisions from 2026-10-14).** Emoji and icons are stripped during layout (`layout.strip_emoji`: post text, cover announcements, video titles), the DB keeps the raw text. Photos in the mosaic only appear at `photo_relevance=3` (`MOSAIC_MIN_PHOTO_RELEVANCE`), framed 16:9 in brief tiles and 3:2 in feature tiles; the cover still uses 2. Long (`BRIEF_SHORTEN_MIN_CHARS`) texts of future brief tiles are shortened by the model by `build_newspaper`, regardless of importance, but lazily — only if the issue doesn't already fit as is (if it fits right away, Gemini isn't called at all); texts already shortened in a previous assembly of the same run (`known_shortened`, from `storage.load_issue_texts`, read before the contents are overwritten) are reused without new calls: the row height is set by its tallest tile; `layout.brief_keys` decides who becomes brief (the tier rule isn't duplicated). A trailing paragraph made up only of markdown links and separators is trimmed as a signature regardless of length.

## The setup wizard in the console

The first run of `scripts/console.py` goes to `/setup` (logic in `setup_wizard.py`, page in `setup_html.py`): Telegram API → account login → Gemini → channels; "Settings" on the home page opens the same wizard. As long as something isn't configured, every other page redirects there (`compute_status()` doesn't fail without `.env`/`channels.yaml`, unlike `load_config()`, which the pipeline still calls as before).

**channels.yaml (Stage 7).** Format: `rubrics: [{name, channels: [...]}]` (order = section order), `channels: [...]` (no section; the old format is just this part), `youtube: [{id: UC..., title, source}]`. There's a single parser, `config.parse_channels_data/read_channels_file` (`ChannelsFile`); `load_config` fills `Config.channels` (all Telegram channels, deduplicated), `rubric_by_channel`, `rubric_order`, `youtube_channels`. The channels card is one textarea, where a `# Name` line is a section heading (`setup_wizard.parse_channels_text/channels_to_text`, line-by-line, so headings with spaces don't break). The "YouTube channels" card is optional (not in `STEP_ORDER`, doesn't affect `compute_status`): on save, `youtube.resolve_channel` looks up `UC...` over the network (the channel page with `Cookie: SOCS=CAI`, otherwise a consent wall; then RSS to verify and get the title); already-saved `source` values aren't re-resolved; any line with an error means nothing is saved. Both cards write to the same file (`save_channels` is atomic) and don't clobber each other. Video collection is `youtube.fetch_new_videos` (RSS, no Shorts, thumbnails in `media_dir()/youtube`), saved into `youtube_videos` by `run_id`, so re-assembling an issue uses the same videos without hitting the network; a collection failure doesn't fail the run.

Where secrets live: `.env` (`TG_API_HASH`, `GEMINI_API_KEY`; written atomically, mode 0600, other lines and comments preserved) and the Telethon session file (0600). Secrets are never logged and never shown in full in the HTML — only as `••••1234`; an empty secret field means "don't change it". There's no bot token anywhere in the project. Telegram login across HTTP requests: the client is reopened on the same session file at every step, and only `phone_code_hash` lives in memory (rationale in `setup_wizard._run_with_client`). For testing in a temp directory: `TG_NEWSPAPER_ENV`, `TG_NEWSPAPER_CHANNELS`, `TG_NEWSPAPER_SESSION_DIR`, `TG_NEWSPAPER_DB`.

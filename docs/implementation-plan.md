# План реализации: TG Newspaper

Пошаговый план реализации из [project-brief.md](project-brief.md). Этапы построены так, чтобы после каждого был работающий и проверяемый кусок системы, а не абстрактный прогресс. Архитектурно это один скрипт, запускающийся по требованию пользователя — кнопкой в локальной консоли или командой в терминале (см. 2. Подписать этот (вспомогательный, не основной личный) аккаунт на все каналы-источники из первого списка.
3. ~~Настроить пробуждение ПК: RTC-будильник в BIOS/UEFI, резерв — Wake-on-LAN.~~ Отменено при пересмотре Этапа 5 — переход на запуск по кнопке снял необходимость будить ПК по расписанию, см. "Запуск" в [project-brief.md](project-brief.md).

6. Составить первый список каналов-источников для конфига.

## Этап 1 — Сбор истории каналов

1. Скрипт через Telethon (`iter_messages` с фильтром по дате) забирает историю каждого канала из списка за фиксированные последние сутки от момента запуска. Наверстывание пропущенных дней сознательно не делается: если прогон не состоялся или упал, тот день просто не печатается, следующий прогон всё равно заберёт только последние сутки.
2. Сохраняет сырые посты (канал, дата, текст, вложения) в хранилище.
3. Ручной прогон на нескольких реальных каналах — сверка с тем, что реально было в канале за период.
4. Базовое логирование: что пришло, за какой период, от какого канала.

## Этап 2 — Фильтрация и дедупликация

1. ✅ Эвристики отсева "не новостей": медиа без подписи/с короткой подписью, пустые посты и прочие явные признаки (список — по итогам просмотра реальных данных, накопленных на Этапе 1).
2. ✅ Интеграция с LLM для классификации спорных случаев (новость/не новость) и для дедупликации новостей, пересказанных разными словами в разных каналах (`classifier.py`, `paraphrase_dedup.py`).
3. ✅ Эвристика на дословные/близкие копипасты — до обращения к LLM (`dedup.py`).
4. ✅ Дедупликация сравнивает кандидатов не только друг с другом внутри прогона, но и со скользящим окном уже опубликованных новостей за последние **5 собранных номеров** (не "5 дней" — после перехода на запуск по кнопке, см. Этап 5, календарные сутки не имеют смысла; и не "5 прогонов" — несколько тестовых прогонов, по которым номер не собирали, вытесняли бы из окна реально напечатанный вчерашний номер) — тем же механизмом (эвристика на копипасту + LLM/эмбеддинги на пересказ), только шире окно сравнения (`history_dedup.py`). "Опубликованное" — это то, что реально вошло в собранный номер, а не `pipeline_outcomes.included=1`: included значит лишь "прошёл отбор", а `pipeline.build_newspaper` часть таких постов выбрасывает из-за нехватки места (`NewspaperResult.dropped`) и часть сокращает нейронкой — новость, не влезшая в номер, не должна завтра блокироваться как "уже была в газете". Поэтому `NewspaperResult.published` хранит финальный набор постов с напечатанным (после сокращения) текстом, `pipeline.save_newspaper_issue` пишет его в таблицу `issue_posts` (`run_id`, `channel`, `message_id`, `text`, `assembled_at`), а `storage.load_recent_issue_posts` отдаёт историю для дедупа — посты из последних 5 прогонов, у которых есть записанный номер. Сборка номера по одному `run_id` может повторяться (`scripts/render_preview.py` гоняют много раз), поэтому повторная сборка **заменяет** состав номера этого прогона, а не дописывает (иначе пост, выпавший при пересборке, остался бы в истории как напечатанный). Вызов `save_newspaper_issue` стоит в `render_preview.py`; печать (Этап 4) должна вызывать его же после сборки. Логика сравнения (`history_dedup.filter_against_history`) не менялась: продолжение сюжета с новыми фактами проходит, кандидата исключают, только если все его факты уже напечатаны. **Миграция:** в уже существующей БД `issue_posts` создаётся пустой, история дедупа пуста до первой сборки номера после этого изменения (прошлые прогоны не восстанавливаются — что из них реально печаталось, нигде не записано). Проверено и офлайн (4 сценария), и вживую: второй реальный прогон подряд корректно распознал пересекающееся окно сбора как уже опубликованное и пропустил в газету только один по-настоящему новый пост.
5. ✅ Прогон на реальных данных, ручная построчная сверка с тем, что было в каналах на самом деле. Сделано на два прогона подряд (144 и то же окно повторно): нашёл и подтвердил на живых данных настоящий пропуск дедупликации пересказов (0.98 схожести эмбеддингов, не попали в один кластер из-за порядко-зависимости complete-linkage) — переключил на single-linkage, перепроверил на том же датасете (10-постовый смешанный кластер разобран верно: 7 оставлено, 3 дубля убраны, старый баг с "техно-хабом" не вернулся). Отдельно нашёл и зафиксировал как известные мелкие огрехи (не чинил): пара постов-исключений, где LLM-классификация непоследовательна на личных постах/анонсах стримов одного автора, и один случай, где LLM без явной причины не сохранила уникальный пост в большой группе. Дополнительно живьём проверена защита от prompt injection на всех трёх LLM-промптах (classify/choose_best/resolve_paraphrase) целенаправленными атакующими постами — ни одна инъекция не сработала.
6. ✅ Оценка `photo_relevance` (тот же батч-вызов LLM-классификации, `classifier.py`): для каждого поста, дошедшего до печати, три степени — 1 (фото не нужно), 2 (уместно, но смысл текста не теряется), 3 (без фото теряется существенная часть смысла). Сами фото/видео агенту не передаются — Telethon даёт только `has_media`/`media_type` (см. `Post` в `storage.py`), само изображение никогда не скачивается, — решение чисто контекстное, по тому, как текст поста ссылается на визуальный ряд (явно исключены видео/кружки/гифки — оценивается только "было бы фото"). Сейчас это только метаданные в отчёте локальной консоли (бейдж в таблице прогона, три разных цвета на каждую степень + отдельная нейтральная заглушка "не оценивалось" для отсеянных постов, которые до классификации не дошли) — вёрстка (`layout.py`) на эту оценку пока не опирается, задел на случай, если в будущем состоянии проекта появятся реальные фото в номере. Хранится в `pipeline_outcomes.photo_relevance` (миграция с более старого булева `needs_photo` — `storage._migrate`).
7. ✅ Прогон на реальных данных подтвердил и заодно вскрыл реальный баг: `GeminiEmbedder.embed` (`paraphrase_dedup.py`) не имел ретраев на транзиентные ошибки — эмбеддинги живут на отдельной, куда более тесной бесплатной квоте (100 запросов/мин) чем текстовая генерация, и прогон падал необработанным `429 RESOURCE_EXHAUSTED` вместо того, чтобы подождать и повторить. Общая логика ретраев (было только в `classifier.py`) вынесена в `gemini_retry.py` и подключена к обоим клиентам.

## Этап 3 — Вёрстка и рендер

1. ✅ Playwright (headless Chromium) поднят, HTML/CSS-шаблон газетной полосы собран (`layout.py`). Вёрстка — мозаичная CSS Grid (broken-column/mosaic, не проточные `column-count` колонки): каждая новость получает "важность" (lead/feature/brief) по объёму текста и соответствующую ШИРИНУ плитки — вперемешку, а не ровными столбцами, как у настоящих газетных полос. Заголовок и текст каждой новости достаются из реального текста поста — ведущий **жирный** markdown-фрагмент (так Telethon форматирует entities в `Message.text`, включая частый эмодзи-префикс перед ним, и включая случай "жирное внутри markdown-ссылки") берётся как заголовок, иначе — первый абзац/строка поста. Декор: орнамент и двойная линейка в шапке, буквица у передовицы, лёгкий растровый узор "под газетную бумагу" в полях, круглый штамп "Тимоха Пресс" и едва заметный водяной вензель "T" на каждой плитке, подвал-колофон с указанием агента-вёрстальщика.
2. ✅ Размер страницы и DPI настроены под точную печать: разметка вся в физических CSS-единицах (мм) — независимо от DPI 1мм шаблона = 1мм бумаги; вьюпорт Playwright и `device_scale_factor` считаются из выбранных page_size (A4/Letter, по умолчанию A4) и DPI (по умолчанию 300) — на Этапе 4 пересчитывать размер не нужно. `.page` — flex-колонка (шапка / мозаика flex:1 / колофон), а не абсолютное позиционирование подвала: так колофон физически не может наехать на мозаику или показать сквозь себя её текст.
3. ✅ Сгенерировано изображение по реальным прогонам (#1 — 67 отобранных новостей, #2 — 1 новость как граничный случай, `scripts/render_preview.py`) и проверено глазами. Финальную визуальную приёмку смотрит пользователь.
4. ✅ Полный текст без обрезки и надёжная многостраничная раскладка (по итогам ревью пользователя): каждая новость печатается ПОЛНОСТЬЮ, без клампинга по числу строк — высота плитки считается по фактическому объёму её текста. Разбивка на страницы — не оценка, а измерение в реальном headless Chromium (`_fit_page`, `render_pages`): каждая страница-кандидат физически рендерится, и то, что не влезло (по `getBoundingClientRect`/`scrollHeight`), переносится на следующую полосу или, для одиночной длинной статьи, сначала расширяется на всю ширину сетки. Передовица и большой штамп — только на первой (титульной) полосе; страницы 2+ — облегчённая "внутренняя" шапка (`running-header`) с номером страницы. Промежуточно проверено на прогоне #1 (67 новостей, 20 полос без единой потерянной или обрезанной новости — построчная сверка с БД для нескольких статей, включая граничные случаи), но неограниченная многостраничность оказалась неверным решением по существу — см. п.5. По пути найдено и исправлено несколько неочевидных багов измерения: водяной знак на плитке (декоративный `::after`, специально торчащий за край) искажал `scrollHeight` и зацикливал подгонку; разный `device_scale_factor` у пробного и финального рендера мог перенести строки текста по-разному; "вырожденный" случай (когда статья не влезала даже в одиночку) принимался без повторной проверки после сжатия.
5. ✅ Фиксированный объём номера + отбор по значимости (пересмотр п.4 по итогам ревью пользователя: "как обычная печатная газета — 4 листа А4, повёрнутые горизонтально", не бесконечная лента). `layout.render_pages` получил `landscape` (альбомная ориентация) и `max_pages` (жёсткий потолок полос, по умолчанию 4, `pipeline.NEWSPAPER_MAX_PAGES`) — что не влезло за `max_pages`, не рендерится вовсе, а возвращается вызывающему коду как список постов. LLM-классификатор (`classifier.py`, тот же батч-вызов, что решает is_news) теперь дополнительно оценивает `importance` (1-5) — по ней выбирается передовица (самая значимая, а не просто самая длинная, `_assign_tiers`) и порядок заполнения полос. Новая `pipeline.build_newspaper` — цикл "собрать → что не влезло → значимое и длинное сократить нейронкой (`GeminiClassifier.shorten`, отдельный LLM-вызов с рубрикой на 1-5) и попробовать снова, незначимое выбросить из номера" — сходится гарантированно (список на сокращение/выброс в каждом раунде строго уменьшается). Проверено на реальных данных прогона #1 с настоящими вызовами Gemini: 67 новостей → importance 1-4 (распределение 3/13/35/16), 4 альбомные полосы, 29 сокращено, 38 выброшено, номер собран за ~2 минуты. По пути найден и исправлен ещё один баг: после того как первая по значимости (короткая) новость становилась передовицей, эвристика подбора партии для полосы (`_seed_batch`) останавливалась слишком рано, если следующая по важности статья не влезала целиком, — оставляя почти всю альбомную полосу пустой, хотя более мелкие статьи из очереди дальше прекрасно бы поместились; `_fill_page` теперь пробует достроить полосу, перебирая остаток по одной и пропуская (не бросая попытки на) те, что не влезли. Сокращённым нейронкой текстам отдельно попросил у LLM короткий заголовок (`ShortenedItem.headline`) и форматирую их как обычный пост с жирным лидом — иначе для однопараграфных пересказов заголовок дублировался в начале тела (та же эвристика, что и для исходных постов, просто не находила короткий первый абзац).

## Этап 4 — Печать

1. Настроить HP Color LaserJet Pro MFP M377dw в локальной сети (AirPrint либо CUPS/IPP-драйвер) — облачная печать для этой модели недоступна (HP закрыла ePrint в январе 2023 года), печатать можно только по LAN.
2. Отправка готового изображения на печать из кода.
3. Обработка очевидных сбоев печати (принтер выключен/недоступен/нет бумаги) — на уровне "не уронить процесс и залогировать", без сложной retry-логики (она — в [future-development.md](future-development.md), если понадобится).
4. **Архив напечатанного.** Перед отправкой на принтер итоговое изображение/PDF полосы сохраняется отдельно (вне репозитория, рядом с `data/tg_newspaper.db` — например `data/archive/<дата-время прогона>/page-N.png`), независимо от того, успешно ли прошла сама печать. Позволяет посмотреть, что печаталось в прошлые прогоны, без повторного рендера. Формат хранения (плоские файлы по датам vs запись в БД с путём к файлу) и политика ротации/очистки старых номеров — на усмотрение реализации, специально не нормируются.

1. ✅ Локальная веб-консоль (`scripts/console.py`) с кнопкой "Собрать газету": по нажатию запускает весь пайплайн (Этапы 1–2: сбор за последние 24 часа от момента нажатия → эвристики → LLM-классификация → дедупликация) и показывает результат тем же экраном, что уже использовался для сверки прогонов. Тот же прогон доступен из терминала (`uv run tg-newspaper`) без браузера.
2. ✅ Логирование прогона: за какой период забраны посты, сколько отсеяно и почему — уже есть (переиспользовано из Этапа 2); при сбое (Telethon/Gemini недоступны) консоль показывает причину, а не падает молча.
3. Когда будут готовы Этапы 3–4 (рендер и печать), встроить их в тот же прогон по кнопке — сейчас консоль показывает только таблицу отбора, а не готовую печатную полосу.
4. Финальная приёмка: несколько прогонов по кнопке подряд (в том числе с большим перерывом между ними) без вмешательства человека, кроме самого нажатия — каждый должен корректно забирать именно свои последние 24 часа и не пытаться наверстать пропуск между прогонами. Это и есть критерий готовности **первой версии**.

## Этап 6 — Персонализация значимости

Была отложенной фичей в future-development.md, пока не появился первый реальный опыт с generic-оценкой `importance` (Этап 3, `classifier.py`) — газета печатается для одного конкретного читателя, а не для широкой аудитории, и эти два понятия значимости расходятся (пример из брифа: новости про CS2/«Властелин колец: Охота на Голлума» с generic-оценкой 2, но потенциально интересные конкретному читателю).

1. ✅ Формат хранения профиля читателя — таблица `reader_profile` в `data/tg_newspaper.db`, ровно одна строка (`id=1`): `interests`/`disinterests` (свободный текст), `onboarded_at` (NULL — онбординг не пройден, прогон по кнопке заблокирован), а также `summary`/`summary_updated_at` — краткий профиль от LLM, который заполнит п.4 (пока только хранится). Читатель один, но `reader_id` сознательно не вводился (multi-user не нужен), и в коде нет ничего под конкретного человека — интересы берутся только из этой таблицы. Рядом — `feedback_surveys` и `feedback_items` (опросы и ответы на них, см. п.3); `storage.load_submitted_feedback` отдаёт все отправленные ответы с текстами постов — примеры для LLM в п.4.
2. ✅ Онбординг при первом запуске (`/onboarding` в консоли): два текстовых поля ("что интересно" / "что неинтересно") и 3 раунда ранжирования по 5 реальных постов из базы (итого 15), на одной странице без JS. Пока онбординг не пройден, главная показывает заметный блок со ссылкой, а `POST /run` не запускает прогон, а редиректит на онбординг; кнопка "Пропустить" ставит `onboarded_at` с пустыми ответами, чтобы запуск не был заблокирован навсегда. Пул для раундов — посты с оценкой модели > 0 из `pipeline_outcomes` (свежие по времени публикации первыми, без повторов между раундами); в пустой базе раунды пропускаются, сохраняется только текст.
3. ✅ Обратная связь после номера: на главной блок "Оцените прошлый номер", пока у последнего прогона с записанным номером (`issue_posts`) нет отправленного опроса. Опрос — 5 постов: 3 из номера и 2 НЕ попавших в номер (`included=1`, но нет в `issue_posts`, т.е. выброшенные из-за нехватки места; если таких меньше двух — добивается из номера), читатель **расставляет их по порядку** (1 — самое важное, места уникальные), а не оценивает по отдельности. Почему ранжирование и почему посты с **разными оценками модели** (по возможности по одному на уровень 1..5; жадно: для уровней 5,4,3,2,1 берётся ближайший по оценке свободный пост с соблюдением квоты 3/2): абсолютные баллы читатель ставит нестабильно и все примерно одинаково, а порядок пяти постов с разной оценкой модели прямо показывает, где его порядок расходится с моделью; если у всех пяти оценка одинаковая, сравнивать нечего. Для онбординга то же правило подбора. Оценок модели и признака "был в номере" на экране ранжирования нет (не подталкиваем: напечатанное кажется важным), порядок показа случайный; элементы опроса фиксируются в БД при первом открытии (повторное открытие — те же 5 постов), `model_score` тоже фиксируется копией, потому что персональная оценка позже изменится. После отправки — страница сравнения: порядок читателя против порядка модели и метрика совпадения Kendall tau-b (при ничьих в оценках модели корректна; не определена, если у модели все оценки равны). Единственное место, откуда берётся "оценка модели", — `feedback.model_score(outcome)` (сейчас `importance`), п.4 подменит её итоговой персональной. Код: `feedback.py` (подбор, метрика), `feedback_html.py` (страницы), `storage.py` (таблицы).
4. **Следующая часть, не сделана.** Второй LLM-вызов или коэффициент поверх текущего generic-importance (`classifier.py`), учитывающий профиль/историю читателя — не замена generic-оценке, общая значимость события всё ещё нужна как база для сравнения между читателями/каналами.
5. Прогон на реальных данных с уже накопленным профилем — сверка, действительно ли отбор полосы сместился в сторону личных интересов, а не просто зашумился.

## Этап 7 — Персонализация по рубрикам

1. Разные каналы группируются в разные секции полосы (например, "мир", "технологии") вместо одного общего потока — требует изменений в `layout.py` (мозаичная раскладка сейчас не знает о рубриках) и в конфигурации списка каналов (у каждого канала — рубрика).
2. Рубрика "вышли новые видео" — отдельная сводка по авторам-персоналиям из списка каналов (например, IgorLinkChannel). Ловить это по тексту Telegram-поста ненадёжно (голая ссылка без подписи отсеивается текущей эвристикой как "нет текста", факт выхода видео можно потерять; автор может вообще не запостить в Telegram) — вместо этого напрямую проверять YouTube-канал автора (YouTube Data API или RSS `videos.xml` по channel_id) и публиковать факт "вышло видео" только когда ролик реально появился на YouTube. Новый источник данных помимо Telethon — отдельный шаг сбора в пайплайне, отдельно от `collector.py`.
3. Прогон на реальных данных — проверить, что рубрики физически умещаются в раскладку 4 альбомных полос (`NEWSPAPER_MAX_PAGES`) наравне с общим потоком новостей, не ломая существующий отбор по значимости.

# Implementation plan: TG Newspaper

A step-by-step implementation plan from [project-brief.md](project-brief.md). The stages are structured so that each one leaves behind a working, verifiable piece of the system, not abstract progress. Architecturally this is a single script, triggered on user demand — by a button in the local console or a terminal command (see "Why MTProto instead of the Bot API" in [../README.md](../README.md)) — the stages below are its sequential parts, not separate processes.

## Stage 0 — Setup

1. Set up a separate Telegram account for the project (a separate phone number — a number already registered to another account can't be reused), get an `api_id`/`api_hash` from my.telegram.org, do an interactive Telethon login under this account once, and store the session file as a secret.
2. Subscribe this (helper, not main personal) account to every source channel on the initial list.
3. ~~Configure PC wake-up: a BIOS/UEFI RTC alarm, with Wake-on-LAN as a fallback.~~ Cancelled when Stage 5 was revisited — switching to button-triggered launch removed the need to wake the PC on a schedule, see "Launch" in [project-brief.md](project-brief.md).
4. Choose and set up the environment — Python, a dependency manager, the repository.
5. Choose storage for state between runs (SQLite is the obvious choice for the first version — simple, no separate service needed): at minimum, the timestamp of the last successful run needs to be kept.
6. Put together the initial list of source channels for the config.

## Stage 1 — Channel history collection

1. A script using Telethon (`iter_messages` with a date filter) pulls each listed channel's history for a fixed last 24 hours from the moment it runs. Catching up on missed days is deliberately not done: if a run doesn't happen or fails, that day just doesn't get printed — the next run still only takes its own last 24 hours.
2. Saves the raw posts (channel, date, text, attachments) into storage.
3. A manual run against several real channels — checked against what was actually posted in the channel during that period.
4. Basic logging: what came in, for what period, from which channel.

## Stage 2 — Filtering and deduplication

1. ✅ Heuristics for filtering out "non-news": media with no caption/a short caption, empty posts, and other clear signals (the list determined by reviewing real data accumulated in Stage 1).
2. ✅ LLM integration for classifying ambiguous cases (news/not news) and for deduplicating news retold in different words across different channels (`classifier.py`, `paraphrase_dedup.py`).
3. ✅ A heuristic for verbatim/near-verbatim copy-pastes — applied before calling the LLM (`dedup.py`).
4. ✅ Deduplication compares candidates not only against each other within a single run, but against a rolling window of already-published news from the last **5 assembled issues** (not "5 days" — after switching to button-triggered launch, see Stage 5, calendar days stop making sense; and not "5 runs" — a handful of test runs that never assembled an issue would push a genuinely printed previous issue out of the window) — using the same mechanism (a copy-paste heuristic plus LLM/embeddings for retellings), just with a wider comparison window (`history_dedup.py`). "Published" means what actually ended up in an assembled issue, not `pipeline_outcomes.included=1`: `included` only means "passed selection" — `pipeline.build_newspaper` drops some of those posts for lack of space (`NewspaperResult.dropped`) and shortens others with the model — a news item that didn't fit in the issue shouldn't be blocked tomorrow as "already in the paper". So `NewspaperResult.published` holds the final set of posts with their printed (post-shortening) text, `pipeline.save_newspaper_issue` writes it to the `issue_posts` table (`run_id`, `channel`, `message_id`, `text`, `assembled_at`), and `storage.load_recent_issue_posts` supplies dedup history — posts from the last 5 runs that have a recorded issue. Assembling an issue for a given `run_id` can be repeated (`scripts/render_preview.py` is run many times over), so re-assembling **replaces** that run's issue contents rather than appending to them (otherwise a post dropped on re-assembly would stay in history as printed). The call to `save_newspaper_issue` lives in `render_preview.py`; printing (Stage 4) should call it too after assembly. The comparison logic (`history_dedup.filter_against_history`) didn't change: a continuing story with new facts passes through, and a candidate is excluded only if all of its facts have already been printed. **Migration:** in an existing DB, `issue_posts` starts out empty, and dedup history is empty until the first issue assembled after this change (past runs aren't backfilled — what was actually printed from them is recorded nowhere). Verified both offline (4 scenarios) and live: a second real run right after the first correctly recognized the overlapping collection window as already published and let only one genuinely new post through into the paper.
5. ✅ A run on real data, with a manual line-by-line check against what was actually in the channels. Done over two runs back to back (144, and the same window again): found and confirmed, on live data, a real retelling-dedup miss (0.98 embedding similarity, not clustered together due to order-dependence in complete-linkage) — switched to single-linkage, re-checked on the same dataset (a 10-post mixed cluster resolved correctly: 7 kept, 3 duplicates removed, the old "techno-hub" bug didn't come back). Separately found and recorded as known minor rough edges (not fixed): a couple of exception cases where LLM classification is inconsistent on one author's personal posts/stream announcements, and one case where the LLM, with no clear reason, failed to keep a unique post in a large group. Additionally verified live that prompt-injection defenses hold across all three LLM prompts (classify/choose_best/resolve_paraphrase) against deliberately adversarial posts — not a single injection worked.
6. ✅ `photo_relevance` scoring (the same batch LLM classification call, `classifier.py`): for every post that reaches print, three levels — 1 (no photo needed), 2 (fitting, but the text's meaning doesn't depend on it), 3 (without a photo, a significant part of the meaning is lost). The photos/videos themselves are never handed to the agent — Telethon only gives `has_media`/`media_type` (see `Post` in `storage.py`); the image itself is never downloaded — the decision is purely contextual, based on how the post's text refers to the visual (videos/video messages/GIFs are explicitly excluded — only "would there be a photo" is scored). For now this is just metadata in the local console's report (a badge in the run table, three different colors per level plus a separate neutral placeholder "not scored" for filtered-out posts that never reached classification) — layout (`layout.py`) doesn't yet rely on this score; it's groundwork in case real photos end up in the issue in some future state of the project. Stored in `pipeline_outcomes.photo_relevance` (migrated from the older boolean `needs_photo` — `storage._migrate`).
7. ✅ A run on real data confirmed things working and, along the way, surfaced a real bug: `GeminiEmbedder.embed` (`paraphrase_dedup.py`) had no retries for transient errors — embeddings live on a separate, much tighter free quota (100 requests/min) than text generation, and the run was crashing with an unhandled `429 RESOURCE_EXHAUSTED` instead of waiting and retrying. The shared retry logic (previously only in `classifier.py`) was pulled out into `gemini_retry.py` and wired into both clients.
8. ✅ Merging a developing story into a single article (user decision from 2026-09-27). Real-data problem: several posts about the same event can appear in one channel in a single day, each with a unique new fact (incident → clarification → retraction) — `resolve_paraphrase_clusters` already deliberately kept all of them (they aren't duplicates — each carries its own fact), but printed them as N scattered articles in different parts of the page instead of as one developing story. Now `pipeline._merge_story_arcs` takes the retelling cluster left over after `_resolve_paraphrase` and groups it by channel: if a SINGLE channel has several posts within the cluster, those are stages of one story, and a new LLM call, `classifier.merge_story_batch`, merges them into a single newspaper article (a headline reflecting the current state, plus a coherent narrative — "it was first reported that... later clarified/retracted..."), which replaces all the original posts in that group (the text of the most recent post serves as the anchor; importance/photo_relevance is the max across the group). The cross-channel case (several DIFFERENT channels reporting different facts about the same event) is deliberately left untouched and still prints as separate posts, as before — merging is limited to a single channel, see `classifier.py`/`pipeline.py` (the new stage `PostOutcome.stage == "story_merge"`).

## Stage 3 — Layout and rendering

1. ✅ Playwright (headless Chromium) wired up, the newspaper-page HTML/CSS template built (`layout.py`). The layout is a mosaic CSS Grid (a broken-column/mosaic layout, not flowing `column-count` columns): each news item gets an "importance" tier (lead/feature/brief) based on text length, and a corresponding tile WIDTH — interleaved, rather than in even columns like a real newspaper page. Each story's headline and body come from the actual post text — a leading **bold** markdown span (how Telethon renders entities in `Message.text`, including a common leading emoji before it, and including the case of "bold inside a markdown link") is taken as the headline; otherwise, the first paragraph/line of the post. Decoration: an ornament and a double rule in the header, a drop cap on the lead story, a subtle "newsprint" halftone texture in the margins, a round "Timokha Press" stamp and a barely visible watermark "T" monogram on every tile, and a footer colophon naming the agent that laid out the page.
2. ✅ Page size and DPI tuned for accurate printing: the entire layout is in physical CSS units (mm) — the template's 1mm is 1mm of paper regardless of DPI; Playwright's viewport and `device_scale_factor` are computed from the chosen page_size (A4/Letter, defaulting to A4) and DPI (default 300) — no size recalculation needed in Stage 4. `.page` is a flex column (header / mosaic flex:1 / colophon), not absolute positioning for the footer — so the colophon physically can't overlap the mosaic or show its text showing through.
3. ✅ An image generated from real runs (#1 — 67 selected news items, #2 — 1 news item as an edge case, `scripts/render_preview.py`) and checked by eye. Final visual acceptance is up to the user.
4. ✅ Full, uncut text and reliable multi-page layout (following the user's review): every news item prints IN FULL, with no line-count clamping — tile height is computed from the actual volume of its text. Pagination isn't estimated, it's measured in a real headless Chromium instance (`_fit_page`, `render_pages`): every candidate page is actually rendered, and whatever doesn't fit (per `getBoundingClientRect`/`scrollHeight`) is carried over to the next page, or, for a single long article, first expanded to the full width of the grid. The front page and the large stamp only appear on the first (title) page; pages 2+ get a lighter "inner" header (`running-header`) with a page number. Interim validation on run #1 (67 news items, 20 pages with not a single lost or truncated item — a line-by-line check against the DB for several articles, including edge cases), but unlimited pagination turned out to be the wrong call on the merits — see item 5. Along the way, several non-obvious measurement bugs were found and fixed: a tile's watermark (a decorative `::after` deliberately overhanging the edge) was distorting `scrollHeight` and looping the fitting process; a different `device_scale_factor` between the trial and final render could reflow text lines differently; a "degenerate" case (an article that didn't fit even on its own) was accepted without re-checking after compression.
5. ✅ Fixed issue length plus importance-based selection (revisiting item 4 after the user's review: "like a regular printed newspaper — 4 landscape A4 sheets", not an endless feed). `layout.render_pages` got `landscape` (landscape orientation) and `max_pages` (a hard page cap, defaulting to 4, `pipeline.NEWSPAPER_MAX_PAGES`) — whatever doesn't fit within `max_pages` isn't rendered at all; it's returned to the calling code as a list of posts. The LLM classifier (`classifier.py`, the same batch call that decides is_news) now additionally scores `importance` (1-5) — used to pick the lead story (the most important one, not just the longest, `_assign_tiers`) and the order pages get filled. The new `pipeline.build_newspaper` is a loop: "assemble → see what doesn't fit → shorten the important-and-long ones with the model (`GeminiClassifier.shorten`, a separate LLM call rated 1-5) and try again, drop the unimportant ones from the issue" — guaranteed to converge (the shorten/drop list strictly shrinks each round). Verified on real data from run #1 with actual Gemini calls: 67 news items → importance 1-4 (distribution 3/13/35/16), 4 landscape pages, 29 shortened, 38 dropped, issue assembled in ~2 minutes. Along the way, another bug was found and fixed: once the first, highest-importance (short) news item became the lead story, the batch-picking heuristic for a page (`_seed_batch`) was stopping too early whenever the next-most-important article didn't fit in full — leaving most of a landscape page empty, even though smaller articles further in the queue would have fit fine; `_fill_page` now tries to top off a page by going through the remainder one at a time, skipping (not giving up over) ones that don't fit. For model-shortened texts, I separately asked the LLM for a short headline (`ShortenedItem.headline`) and format them like a regular post with a bold lead — otherwise, for single-paragraph retellings, the headline duplicated the start of the body (the same heuristic as for original posts simply wasn't finding a short first paragraph).

**Capacity improvements (2026-10-14).** Real run #7 (62 news items passed selection) only printed 11 out of 62, with the last mosaic pages left empty. Diagnosis showed that a row of three brief tiles with 3:2 photos and long texts takes up 20–38 row-units out of roughly 74 per page — nearly a whole landscape page (row height is set by its tallest tile). An experiment on the same data (how many rows fit on 2 pages): as-is, 6; without photos, 8; without photos and with short texts, 14. By the user's decisions: the mosaic now goes up to 6 pages (was 4), with the cover on top of that; when there's nothing left to shorten, a binary search finds the largest number of the most important news items that fits (previously `len(leftover)` was dropped all at once, leaving pages empty); photos in the mosaic only at `photo_relevance=3` ("meaning is lost without a photo"), framed 16:9 in brief tiles, still 2 on the cover; long (over 600 characters) texts of future brief tiles are pre-shortened by the model regardless of importance; emoji and decorative icons are stripped during layout (the DB keeps the raw text); a post's trailing paragraph made up only of links is trimmed as a signature regardless of length. Also: the issue date and PDF filename follow the computer's timezone, a Morning/Afternoon/Evening/Night edition appears on the cover and page headers, and the MIN_ISSUE_NEWS threshold (8 at the time, later replaced by `layout.COVER_MIN_ARTICLES` = 10: exactly that many cover slots). Results on run #7, step by step: started at 11 of 62; 6 pages plus binary search gave 15; photos only at level 3, 16:9 briefs, pre-shortening, and emoji cleanup gave 42 of 62. Every news item scored 4–5 got printed. **Known limitation:** roughly 1/5 of a page's height is left empty at the bottom of every page: the next row doesn't fit in what's left and moves to the next page (see "Deferred features" in future-development.md).

**Code-review fixes (2026-10-14, version 0.1.4).** Intermediate layout passes inside `build_newspaper` are now fit-only (`render_pages(fit_only=True)`: no cover, no LLM, no screenshots, no disk writes); there's exactly one full render into the issue directory — previously a failed early attempt left stray `page_N.png` files behind, which ended up in the preview and PDF. Pre-shortening briefs now happens only if the issue doesn't already fit as is; texts already shortened in a previous assembly of the same run are read from `issue_posts` without a repeat Gemini call; posts Gemini failed to return get a second attempt. If the final render still can't fit a news item, it's no longer recorded as part of the issue's contents (otherwise dedup would end up dropping something that was never actually printed). `strip_emoji`: bold-markdown cleanup now runs across the whole text (adjacent `** **` from two bold spans used to glue words together), a link made up only of emoji is now removed along with its URL, and a line consisting of a single emoji no longer splits a paragraph in two. The tier rule is now one single function, `layout._tier_for_rank`; the issue threshold is `layout.COVER_MIN_ARTICLES` (10).

## Stage 4 — Printing

1. Set up the HP Color LaserJet Pro MFP M377dw on the local network (AirPrint or a CUPS/IPP driver) — cloud printing is unavailable for this model, so printing is LAN-only.
2. Send the finished image to print from code.
3. Handle obvious print failures (printer off/unreachable/out of paper) — at the level of "don't crash the process, log it", without complex retry logic (that's in [future-development.md](future-development.md), if it turns out to be needed).
4. **Printed archive.** Before sending a page to the printer, the final image/PDF is saved separately (outside the repo, next to `data/tg_newspaper.db` — e.g. `data/archive/<run date-time>/page-N.png`), regardless of whether the print itself succeeded. This makes it possible to look back at what was printed in past runs without re-rendering. The storage format (flat files by date vs. DB rows with a file path) and the rotation/cleanup policy for old issues are left to the implementation — deliberately not specified here.

The same run is also available from the terminal (`uv run tg-newspaper`), with no browser.

4. ✅ (rendering; printing from Stage 4 is still not done) Rendering is built into the run: the "Assemble newspaper" button and `uv run tg-newspaper` lay out the issue right after selection (`pipeline.assemble_issue`, files in `data/issues/run_<id>/`), and the run page shows page previews and serves PDFs (per-page A4 and merged A3 sheets, `issue_pdf.py`, the cache is built on first download); there's a manual re-render (`POST /run_<id>/render`). ## Stage 6 — Importance personalization

Used to be a deferred feature in future-development.md, until there was real experience with the generic `importance` score (Stage 3, `classifier.py`) — the newspaper is printed for one specific reader, not a broad audience, and these two notions of importance diverge (an example from the brief: news about CS2/"The Lord of the Rings: The Hunt for Gollum" scored 2 generically, but potentially interesting to a specific reader).

1. ✅ Reader profile storage format — a `reader_profile` table in `data/tg_newspaper.db`, exactly one row (`id=1`): `interests`/`disinterests` (free text), `onboarded_at` (NULL means onboarding isn't done, and the button-triggered run is blocked), plus `summary`/`summary_updated_at` — a short LLM-generated profile, to be filled in by item 4 (for now it's just storage). There's one reader, but a `reader_id` was deliberately not introduced (multi-user isn't needed), and nothing in the code is hardcoded to a specific person — interests come only from this table. Next to it: `feedback_surveys` and `feedback_items` (surveys and their answers, see item 3); `storage.load_submitted_feedback` returns all submitted answers along with the posts' text — examples for the LLM in item 4.
2. ✅ Onboarding on first run (`/onboarding` in the console): two text fields ("what's interesting" / "what isn't") and 3 rounds of ranking 5 real posts from the database each (15 total), on a single page with no JS. Until onboarding is done, the home page shows a prominent block with a link, and `POST /run` doesn't start a run — it redirects to onboarding; a "Skip" button sets `onboarded_at` with empty answers so the run isn't blocked forever. The pool for the rounds is posts scored > 0 by the model from `pipeline_outcomes` (most recent by publish time first, no repeats across rounds); on an empty database, the rounds are skipped and only the text fields are saved.
3. ✅ Feedback after an issue: on the home page, a "Rate the last issue" block, shown while the most recent run with a recorded issue (`issue_posts`) has no submitted survey yet. The survey has 5 posts: 3 from the issue and 2 that did NOT make it in (`included=1` but absent from `issue_posts`, i.e. dropped for lack of space; if fewer than two such posts exist, the rest are filled in from the issue), and the reader **ranks them in order** (1 being most important, each rank unique), rather than scoring them individually. Why ranking, and why posts with **different model scores** (as evenly as possible across levels 1..5; greedily: for levels 5,4,3,2,1, the nearest-scoring free post is taken, respecting a 3/2 quota): readers give unreliable absolute scores and tend to rate everything about the same, while the order of five posts with different model scores directly shows where the reader's ordering diverges from the model's; if all five have the same score, there's nothing to compare. Onboarding uses the same selection rule. Neither the model's scores nor the "was in the issue" flag appear on the ranking screen (so as not to bias the reader: printed things tend to feel important), display order is randomized; survey items are fixed in the DB the first time the page is opened (reopening shows the same 5 posts), and `model_score` is also frozen as a copy, since the personal score will change later. After submitting, there's a comparison page: the reader's order against the model's order, plus Kendall's tau-b as the match metric (handles ties in model scores correctly; undefined if the model's scores are all equal). The single place "the model's score" is read from is `feedback.model_score(outcome)` (currently `importance`); item 4 will swap it for the final personal score. Code: `feedback.py` (selection, metric), `feedback_html.py` (pages), `storage.py` (tables).
4. ✅ A personal score layered on top of the generic one (`personalization.py`, `classifier.py`, `pipeline.py`) — not a replacement for generic importance (it stays the baseline; its definition in the prompt is unchanged), but a second score, `personal_importance` (1–5, "interesting to THIS specific reader"). **Why in the same call:** a separate request for the personal score would double the burn rate on Gemini's free daily quota, and the model already gets the context (the post text) anyway; so, when the profile isn't empty, a block about the reader is appended to classification's `system instruction`, and a field is added to the response schema (separate wire schemas, `_WireItem`/`_WirePersonalItem`, so the field with a default doesn't leak into `response_schema` when unused). The block: the questionnaire (interested/not interested), the short `summary` profile, and examples from the last `EXAMPLE_SURVEYS_LIMIT=8` rankings ("the reader ranked it this way: 1. ... 2. ...", texts truncated to 300 characters, alongside the model's score at the time — the mismatch between the reader's order and that score is the main signal); the questionnaire, summary, and post texts are explicitly labeled as data, not instructions (a separate prompt-injection defense, since the questionnaire is written by a human). **An empty profile** (no texts, no summary, no submitted surveys) adds nothing to the prompt, `personal_importance` isn't requested, the final score equals the generic one, weight 0: the newspaper behaves exactly as before. **The final score** is `final_importance(generic, personal, weight) = round-half-up(weight·personal + (1−weight)·generic)`, clamped to 1..5; weight = `min(0.7, 0.3 + 0.05·number_of_submitted_surveys)`: the questionnaire alone is a weak but real signal (starting at 0.3), each survey adds 0.05 (the 3-round onboarding alone gives ~0.45), and the 0.7 ceiling keeps the generic score as an anchor, so genuinely major events still break through even if the reader doesn't care for them. In `pipeline_outcomes`, there are `personal_importance` and `final_importance` columns (0 means unknown for old runs, migrated in `_migrate`); selection, shortening, `IMPORTANCE_DROP_THRESHOLD`, and tile size in `build_newspaper` all go through the single helper `pipeline.effective_importance` (the final score, falling back to generic when it's 0); `feedback.model_score` was switched to the same helper. **The short `summary` profile:** `GeminiClassifier.summarize_profile` (questionnaire + previous summary + all feedback, most recent first, size-limited → up to ~10 lines about taste, without verbatim retelling of posts); it's updated lazily inside `run_pipeline_for_last_24h`, BEFORE classification, once `summary_updated_at` is at least `SUMMARY_EVERY_SURVEYS=3` surveys stale; an update failure is logged and the run proceeds with the old summary; Gemini is never called from the console's survey handlers. In the console: the run page shows the generic / "for you" / final scores side by side (old runs show only the generic one), and the home page shows an "is the newspaper learning" indicator (survey count, the average tau-b match of the last 5 surveys against the previous 5, no charts, no JS).
5. A run on real data with an already-accumulated profile — checking whether page selection has actually shifted toward personal interests, rather than just gotten noisier. **Not done yet:** this needs a real reader profile (completed onboarding and several post-issue surveys) and live Gemini calls; item 4 has only been verified against a fake model and temporary databases.

## Stage 7 — Section-based personalization

1. ✅ Different channels are grouped into different page sections (e.g. "world", "tech") instead of one combined stream — required changes in `layout.py` (the mosaic layout previously had no concept of sections) and in the channel-list configuration (each channel now has a section).
2. ✅ A "new videos just dropped" section — a separate roundup for persona-channel authors from the channel list (e.g. IgorLinkChannel). Catching this from Telegram post text isn't reliable (a bare link with no caption gets filtered out by the current heuristic as "no text", so the fact of a new video can be missed; and the author might not post to Telegram at all) — instead, check the author's YouTube channel directly (the YouTube Data API or the `videos.xml` RSS feed by channel_id), and only publish "a video dropped" once the video actually shows up on YouTube. A new data source besides Telethon — a separate collection step in the pipeline, apart from `collector.py`.
3. ✅ A run on real data — checking that sections physically fit into the 4-landscape-page layout (`NEWSPAPER_MAX_PAGES`) alongside the regular news stream, without breaking existing importance-based selection.

**How it was built.** Sections are defined in `channels.yaml` (`rubrics: [{name, channels}]`; the old flat `channels:` list is still read as before), and in the wizard, as `# Section` heading lines in the same textarea. In the issue, each section is a block with a heading plate, in config order (channels with no section go last, under a "Misc" section); when spilling onto the next page, the heading repeats with "(continued)", and never gets orphaned at the bottom of a page. One lead story per issue, and tile tiers, are still decided globally by importance. Video isn't sourced from Telegram posts at all, but directly from YouTube: a separate, optional wizard card (`@handle`/link/`UC...` → resolved to an id via the channel page, verified via RSS), collected after post selection within the same run window via public RSS with no API key, Shorts excluded, `mqdefault` thumbnails downloaded to `data/media/youtube`, videos tied to the run (`youtube_videos`). The "New videos" block is the last section on the last mosaic page, with space reserved for it — news items can't push it out. So that, with sections, running short on space doesn't drop the tail of the last section (even if it's important), `build_newspaper` now drops the least important news across the whole issue instead. Details in [../AGENTS.md](../AGENTS.md).
